Phase: Kymaean App + Website Design Synthesis — after CSI-R1 whole-Stage semantic integration

## 0. Purpose

CSI-R1 demonstrated that the accepted Stage semantics can coexist, but also showed that semantic correctness can still accumulate into a dashboard perimeter around the living Production.

SPR-01 therefore does not invent another subsystem. It reduces visible persistence.

The central question is:

> **What is the smallest persistent visible Stage surface that preserves scope, human identity, disclosure, agency, opportunity, truthful context access, and accessibility without duplicating information or surrounding the Production with system chrome?**

## 1. Governing law

> **Persistence is earned by ambiguity prevention, not by conceptual importance.**

A Stage element deserves continuous visible presence only when removing it would create a material ambiguity about at least one of:

- current Production scope;
- active Scene;
- Character identity;
- disclosure perspective;
- creator agency/posture;
- current authoritative opportunity/salience;
- blocking capability;
- current-versus-historical locus;
- safe return/navigation from an already-open transient surface.

If an element is needed only in a particular state, it is **CONTEXTUAL**.

If it is needed only after deliberate inspection, it is **ON DEMAND**.

If it adds no necessary task truth, duplicates stronger information, imports unsupported semantics, or creates misleading state affordance, it is **REMOVE**.

SPR adds one reduction law:

> **Semantic persistence does not require visual duplication.**

---

## 2. Classification vocabulary

SPR uses exactly four design classifications. These are design allocation labels, not implementation enums.

### PERSIST

Continuously recoverable in the live Stage because its absence would ordinarily break scope, identity, or basic continuity.

Persistence may be visually quiet. `PERSIST` does not mean large, carded, colorful, or duplicated.

### CONTEXTUAL

Visible/recoverable only while a current condition makes it materially relevant.

Examples include a Character-bounded perspective cue, active Current Opportunity, task-specific posture, or blocking capability state.

### ON DEMAND

Absent from the default Stage until the creator deliberately follows meaning or opens a durable application-level task.

### REMOVE

Not part of the live Stage contract in the tested form. Removal may be because the element is redundant, ungrounded, misleading, promotional, schema-complete, or architecturally misplaced.

## 3. Stage presence matrix

### 3.1 Living Production field

| Element | Classification | Reason |
|---|---|---|
| People / living relational field | **PERSIST** | The Stage is first a living human Production. Removing the people destroys the primary experience rather than merely hiding metadata. |
| Character identity semantics for people currently present | **PERSIST** | People must remain specifically identifiable and accessible. Identity may be carried by the living field plus accessible labels/invariants; no duplicate roster is implied. |
| Duplicate permanent portrait-chip roster when the living field already identifies the same people | **REMOVE** | Duplicates identity rather than preserving it. Repetition is not semantic continuity. |
| Decorative Character status dots without a defined authoritative meaning | **REMOVE** | State-looking decoration invites false interpretations such as readiness, turn state, attention, or availability. |
| Relationship graph/connectors/halos as standing visualization | **REMOVE** | Relationship is composition, not a permanent diagram. |

### 3.2 Scope and continuity

| Element | Classification | Reason |
|---|---|---|
| Current Production identity | **PERSIST** | The user must know which persistent creative object they are inside. It should be quiet and may live at shell/title semantics rather than as a decorative heading. |
| Active Scene identity when a Scene exists | **PERSIST** | Prevents current-scope ambiguity and supports return/focus continuity. |
| Kymaean product wordmark/logo inside the Stage content field | **ON DEMAND / APPLICATION-SCOPE**, not Stage-persistent | Product identity belongs at the application/scope layer and need not compete with Production identity during continuous work. Exact shell treatment remains open. |
| Current-versus-historical locus | **CONTEXTUAL** | Current is the default and usually needs no label. Historical locus becomes explicit when entering history or when ambiguity is possible. |
| Generic Stage marketing/tagline copy | **REMOVE** | It does not express current Production truth or creator task state. |

### 3.3 Perspective and creator agency

| Element | Classification | Reason |
|---|---|---|
| Presentation Perspective cue | **CONTEXTUAL** | Must be recoverable whenever disclosure materially differs. It need not occupy equal weight when perspective is obvious or unrestricted. |
| Creator Posture cue | **CONTEXTUAL** | Must be recoverable when agency materially differs. Watch/Perform must never be conflated, but posture need not become a permanent mode bar. |
| `(You)` attached to a Character name as perspective shorthand | **REMOVE** | It conflates perspective with creator embodiment/agency. |
| Universal Watch/Direct/Perform/Write tab strip | **REMOVE** | Postures are not four product silos and commands should follow the current task. |
| Perform portrayal input | **CONTEXTUAL** | Appears because agency changed to Perform; it must not exist permanently in Watch. |

### 3.4 Current Opportunity and action truth

| Element | Classification | Reason |
|---|---|---|
| Current Opportunity semantic cue | **CONTEXTUAL** | Visible/ambient while materially active because its absence can hide current authority/salience. |
| `Response is not required` clarification | **CONTEXTUAL** | Appears when needed to prevent opportunity -> obligation inference; not necessarily repeated everywhere. |
| Large gameplay-like turn card/token treatment | **REMOVE AS DEFAULT FORM** | The semantic fact survives; the tested visual form risks turn-order/game semantics and gains no inheritance rights. |
| Task-specific creator commands | **CONTEXTUAL** | Commands follow current object/task/posture. |
| Universal command ribbon | **REMOVE** | Accumulates operations unrelated to the current human situation. |

### 3.5 Context and answers

| Element | Classification | Reason |
|---|---|---|
| Meaning-linked context invocation affordance | **CONTEXTUAL** | Appears at the current anchor/question source when useful; it is not a global `Context` destination. |
| Context answer surface | **ON DEMAND** | Opens only after deliberate invocation and returns to the same Stage. |
| One exact contextual question | **ON DEMAND** | Exists only while the context task is active. |
| Supported answer | **ON DEMAND** | Exists only for the invoked question. |
| Exact authority boundary | **ON DEMAND / CONDITIONAL** | Appears only when necessary to prevent a false inference. |
| Supporting basis | **ON DEMAND / CONDITIONAL** | Appears only when it adds distinct necessary support. |
| Generic `About This Answer` explanation | **REMOVE BY DEFAULT** | Trust machinery should govern behavior more strongly than it occupies the interface. |
| Inaccessible/private-category placeholders or explanations | **REMOVE** | Bounded perspective becomes quieter through subtraction. |
| Generic `Ask anything about C` continuation | **REMOVE** | Pushes the product toward entity-chat/database interaction rather than meaning-following Production navigation. |
| Return/Back from open context | **CONTEXTUAL** | Required while context is open; absent when there is nothing to return from. |

### 3.6 History and causal explanation

| Element | Classification | Reason |
|---|---|---|
| Causal/history route for the exact requested explanation | **ON DEMAND / CONDITIONAL** | Offered only when that explanation is authoritatively available. |
| Permanent history/causal timeline | **REMOVE FROM DEFAULT STAGE** | History is deep/on-demand and must not silently become current state. |
| Current/history status badge always visible | **REMOVE** | Current is default; history should become explicit when entered. |
| TEO-style earlier/later comparison | **ON DEMAND** | A causal-observability resource where useful, not Stage structure. |

### 3.7 Transcript, evidence, provenance, capability

| Element | Classification | Reason |
|---|---|---|
| Recent Performance/transcript | **ON DEMAND / FUTURE AUTHORITY DEPENDENT** | Patch 0014 canonical Context v2 currently keeps `recentPerformances = []` and `RecentPerformanceText` empty. No permanent transcript is authorized. |
| Evidence taxonomy / Character dossier | **REMOVE FROM DEFAULT CONTEXT MODEL** | Context is question-bounded, not schema-complete. Deep specialist views may later be separately justified but do not inherit this taxonomy. |
| Engineering provenance such as StateHash/ContextPacketId/source lane | **ON DEMAND FOR SPECIALIST/DIAGNOSTIC TASKS** | Never ordinary fictional/Character-facing text. |
| Provider/model/cost/NPU telemetry | **ON DEMAND** | Technical diagnostics, not dramatic Stage state. |
| Blocking capability state | **CONTEXTUAL** | Visible only when it materially blocks or changes the current task. |
| Non-blocking technical capability status | **ON DEMAND** | Does not deserve ambient Stage presence. |
| Confidence meter / traffic-light truth system | **REMOVE** | Deterministic authority boundaries are not model confidence. |

### 3.8 Navigation and application chrome

| Element | Classification | Reason |
|---|---|---|
| Durable Production selection/exit/app settings access | **ON DEMAND / APPLICATION-SCOPE** | This remains valid shell navigation but should not become a competing Stage taxonomy. |
| Minimal application-scope navigation affordance | **PERSIST OR CONTEXTUAL AT SHELL LEVEL**, exact form open | The user must retain a safe route to durable scope navigation, but the Stage does not require a full menu always expanded. |
| `PEOPLE / CONTEXT / PROGRESS` | **REMOVE** | `Context` should follow meaning; `Progress` is not an accepted Production primitive; the set recreates generic application silos. |
| Search/menu/avatar controls | **ON DEMAND / TASK-JUSTIFIED** | No persistence right from renderer convention. Each must be justified by an actual app-level task. |
| Generic AI composer in Watch | **REMOVE** | Watch remains useful without permanent text input. |

## 4. Reduced closed-Stage contract

After reduction, the default Stage may need only:

```text
CURRENT PRODUCTION / ACTIVE SCENE

LIVING PEOPLE + RELATIONAL SITUATION

[Perspective — only if materially necessary]
[Posture — only if materially necessary]
[Current Opportunity — only while active]
[Blocking capability — only if relevant]
[Current task commands — only if earned]
```

Everything in brackets is conditional.

The Stage must still be programmatically navigable and accessible even when visual chrome is minimal.

Candidate law:

> **The closed Stage should expose the smallest set of truths whose absence would change what the creator thinks they are seeing, what they are allowed to do, or whose perspective constrains disclosure.**

---

## 5. Reduced context-open contract

Context opening adds only what the invoked task requires:

```text
retained live Stage
+
invoking anchor / exact question
+
supported answer
+
[exact authority boundary — only if needed]
+
[one justified next route]
+
return
```

No additional persistent roster, evidence taxonomy, provenance lecture, confidence system, or global `Context` navigation is required.

If the answer itself is enough, the answer should not be surrounded by empty structural sections merely to preserve a component template.

---

## 6. Semantic versus visual persistence

SPR distinguishes three different obligations that previous renders sometimes collapsed:

1. **semantic persistence** — the truth remains recoverable;
2. **visual persistence** — the truth is continuously visible;
3. **visual duplication** — the same truth appears in multiple places/forms.

Required rule:

> **Semantic persistence may be satisfied by one quiet, accessible representation. Duplicate visual representations require separate justification.**

Examples:

- Character identity may persist through the living representation plus accessible name semantics; a second portrait roster is not automatically required.
- Production/Scene may persist in a quiet title/scope region; a large branded heading is not required.
- Perspective may be programmatically exposed and visually shown only when it materially differs; it need not become a permanent mode banner.

---

## 7. State-like decoration prohibition

CSI-R1 exposed ambiguous colored Character dots.

SPR freezes the correction:

> **Any visual treatment that plausibly reads as application or fictional state must have a defined semantic contract, accessibility equivalent, and authoritative source—or it is removed.**

This applies to:

- colored dots;
- halos;
- rings;
- pulses;
- badges;
- meter fills;
- status lights;
- persistent color coding;
- animation implying readiness, attention, tension, relation, or causality.

Decorative visual richness remains allowed when it does not masquerade as authoritative state.

---

## 8. Brand and Stage separation

Kymaean's product identity may be strong at launch, application scope, marketing, empty states, and other appropriate moments.

SPR does not remove brand identity from the application.

It instead establishes:

> **Inside an active Production, product branding must not outrank the Production itself by default.**

Exact title-bar, app-shell, icon, or wordmark treatment remains open and must later be tested against Windows-native shell needs.

Marketing statements are not current Production information and therefore do not belong inside the live Stage by default.

---

## 9. Global navigation boundary

The accepted shell grammar remains authoritative:

> **Navigate between durable scopes; transition within one Production by following meaning.**

Therefore:

- Production selection/lifecycle, settings/help/diagnostics may remain durable application-scope destinations;
- possibility/performance/history do not become global silos by default;
- People/Context/Progress do not become global silos;
- perspective is not top-level navigation;
- posture is not top-level navigation;
- Character context begins at a meaningful Character/current anchor;
- causal history begins from an answerable current `Why?` or deliberate history task, not because a global History tab is always present.

---

## 10. Accessibility requirements under reduction

Reduction must never mean inaccessible hiding.

The reduced Stage must remain semantically coherent without:

- portrait recognition;
- color;
- motion;
- precise spatial arrangement;
- simultaneous wide columns.

Required recoverability:

- current Production identity;
- active Scene identity;
- Character identities;
- active perspective when material;
- active posture when material;
- Current Opportunity when active;
- opportunity != obligation;
- context invocation;
- current context heading/question;
- exact answer/boundary text;
- predictable return target;
- blocking capability when relevant.

Visual quietness must be paired with programmatic names, roles, states, relationships, and focus order where appropriate.

---

## 11. ARM64 / quiescence

SPR strengthens the low-idle-cost direction.

Fewer persistent surfaces reduce reasons for:

- continuous data recomputation;
- idle layout/animation work;
- speculative answer generation;
- background context summarization;
- relationship graph rendering;
- provider polling;
- persistent GPU/NPU activity.

At rest, the Stage should be driven by already-authoritative local state and explicit changes.

No Windows AI/NPU runtime behavior is claimed or required by SPR-01.

---

## 12. Surface quarantine

SPR selects no final visual style.

No inheritance rights for:

- CSI-R1 photoreal meeting-room surface;
- exact cast/names/faces/clothing;
- portrait rows;
- status dots;
- cream/white panel language;
- green Opportunity card;
- top-right navigation;
- exact top bar;
- wordmark scale/placement;
- search/menu/avatar geometry;
- marketing copy;
- right-side inspector;
- rounded cards;
- city-window/café/office atmosphere;
- generic productivity/SaaS styling.

> **Surface != law.**

## 13. Falsification criteria for a later reduction render

A future SPR-R1 render is warranted only after Director approval.

It should test exactly whether the reduced allocation works:

1. Are people/relationship unquestionably first read?
2. Can the user recover Production and Scene with much less chrome?
3. Are Character identities accessible without a duplicate permanent portrait roster?
4. Is perspective recoverable when material without `(You)` or a mode banner?
5. Is posture recoverable when material without permanent posture tabs?
6. Is Current Opportunity clear while visually quieter and still non-obligatory?
7. Are all ambiguous status dots/state decorations gone?
8. Is global `PEOPLE / CONTEXT / PROGRESS` absent?
9. Is Stage marketing copy absent?
10. Can context still be invoked from meaning rather than global navigation?
11. When context is open, is the answer the minimum question -> truth -> necessary boundary -> return form?
12. Does the Stage feel like one Production rather than a scene surrounded by application chrome?
13. Does the concept remain understandable without color/motion/portrait recognition?
14. Is all technical provenance/capability machinery absent unless task-relevant?

Exactly one unrefined reduced Stage state should be sufficient for the first probe. No automatic correction chain.
