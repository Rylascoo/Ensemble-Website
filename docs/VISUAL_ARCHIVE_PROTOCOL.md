# Kymaean Website Artwork — Visual Archive & Handoff Protocol

Status: **ACTIVE PROJECT LAW FOR WEBSITE / BRAND ARTWORK HANDOFFS**

Updated: 2026-09-02

Purpose: prevent visual-development knowledge from disappearing when a project chat, experiment, or branch is retired while preserving a genuinely clean active discovery workspace.

## Core law

A website-artwork handoff is **not complete** until the current chat's visual output, user signals, design judgment, asset state, and project authority have been reconciled into canonical Google Drive and GitHub state.

Governing principles:

> **Preserve the concept, the evidence, and the judgment. Control when the picture is reopened.**

> **Preserve the lineage. Restart the search.**

Google Drive `Ensemble Project` remains visual-master and human-readable creative-continuity authority. GitHub records protocol, current checkpoint, implementation-facing specifications, and active handoff/current-state authority.

## 2. New-material intake rule

Anything in `00 Unreviewed — Drop New Material Here` is uninterpreted evidence.

When reconciling intake:

1. inspect in project context;
2. determine lineage/category;
3. recover provenance, chronology, concept identity, user reaction, and prior design judgment where available;
4. update `Kymaean Visual Exploration Registry & Critique Ledger`;
5. classify historical material into the Historical Inspiration Library, preserving binary/source material whenever possible;
6. classify genuinely new active work into the Clean-Slate workspace only when intended for the current search;
7. move or mark processed intake as reconciled;
8. never silently promote historical material into current convergence/incumbency.

For a deliberately independent clean-slate experiment, do not inspect new visual intake before the first independent work unless the user explicitly asks to interpret it first.

## 3. O0 Original Concept Foundation rule

Recovered original Ensemble artwork/source files remain under O0 as a major conceptual ancestor, not a selected style.

Preserve transferable discoveries such as persistent character presence, social geometry, bounded perspective, distinct identity without merger, causal Archive/history, theatrical/literary typography, information asymmetry, and distributed identity across cast/word/stage/perspective/consequence/history.

Do not grant inheritance rights to O0's exact dark ground, gold/amber, serif treatment, character colors, constellation/particle imagery, island imagery, three-person geometry, borders, icons, compositions, or layouts.

## 4. Required classification

For every meaningful experiment, historical branch, checkpoint, or retired branch, distinguish:

- **USER SIGNAL** — explicit user reaction/preference;
- **DESIGN JUDGMENT** — Director/design-team evaluation;
- **GENERATED-BOARD EVALUATION** — conclusions/scores embedded in generated collateral, when relevant;
- **STATUS** — active research, completed checkpoint, conceptual ancestor, historical benchmark, promising research, failure evidence, rejected manifestation, superseded surface, selected only if explicitly selected, or another precise state;
- **ASSET STATE** — standalone binary archived, embedded archival visual copy, binary pending recovery, intentionally unavailable, or another exact state;
- **TRANSFERABLE DISCOVERY** — principle/visual physics worth preserving;
- **SURFACE QUARANTINE** — appearance that has no inheritance rights.

Never convert praise, assistant preference, recency, repetition, development cost, or a generated board's score into user approval.

## 5. Mandatory pre-handoff audit

Before finalizing any website/brand artwork handoff, audit the retiring chat for:

1. every generated artwork/materially distinct visual variant available to the Director;
2. failed generations with diagnostic value;
3. experiment/round identifiers;
4. explicit user reactions, including praise, dislike, concern, humor with diagnostic meaning, favorites, rejection, and preservation requests;
5. Director/design-team judgments and comparative critiques;
6. generated-board rankings, clearly separated from user approval;
7. convergence/divergence decisions;
8. durable discoveries;
9. surface vocabulary to quarantine rather than inherit;
10. exact asset lineage/availability;
11. process discoveries about renderer context, prompt behavior, memory assumptions, or tool limitations when those materially affect future work;
12. whether the research branch itself is ending or only the current chat is ending.

Do not summarize only the latest or strongest branch. Preserve materially relevant competing/contradictory evidence that explains direction changes.

## 6. Chat handoff vs branch retirement

These are different events.

### A. Chat handoff while the active branch continues

Use this when the current project chat is saturated or being replaced, but the same active R0 research branch/gate continues.

Required actions:

1. finish/evaluate the current checkpoint;
2. audit the chat;
3. preserve available visual evidence in the active Drive lane/checkpoint;
4. update the critique registry;
5. update Drive continuity law if project law changed;
6. create/update a checkpoint artifact and fresh-chat handoff;
7. update GitHub checkpoint, active handoff, and `CURRENT_STATE.md`;
8. verify all references;
9. retire the old chat while the branch remains in `03 Clean-Slate Visual Discovery — Active`.

**Do not move an ongoing branch into Historical Inspiration merely because its Director chat is being replaced.**

### B. Branch/phase retirement

Use this only when the branch or phase itself is complete, superseded, or intentionally closed.

Then:

1. finish evaluation;
2. audit assets/signals/judgments;
3. reconcile intake;
4. transfer the completed branch into the appropriate historical lane under `02 Historical Inspiration Library — Prior Visual Branches` with precise phase/provenance naming;
5. preserve failures as failures;
6. update the registry and continuity law;
7. update GitHub current state/active handoff;
8. verify no active reference still treats the retired branch as current.

Historical assets do not silently migrate back into active lanes. Deliberate revival must be labeled.

## 7. Binary / embedded-visual rule

Preserve every **available** meaningful visual result in Drive before handoff completion when the available connector/tool path permits it.

Preferred asset-state order:

1. standalone original/raw binary in Drive when upload is actually supported;
2. otherwise an embedded archival visual copy in a clearly labeled Drive atlas/checkpoint when the conversation-local bytes can be embedded but not uploaded as standalone files;
3. otherwise concept/evaluation record marked **ASSET PENDING RECOVERY** with retrieval clues.

Never call an embedded image a standalone raw-file archive.

Never claim binary completeness when the tool path did not create standalone binaries.

If an older binary cannot be recovered:

1. preserve the concept/evaluation record;
2. mark **PENDING RECOVERY**;
3. retain source title/file identifier/retrieval clues;
4. never imply recovery until actually verified.

## 8. Renderer-Isolation archive rule

For R0 Renderer Isolation:

- the persistent Ensemble project is Director Context;
- each clean-slate image normally comes from a fresh regular non-project Renderer Context;
- one image per renderer chat is the preferred discipline;
- the renderer chat may be disposable, so visual evidence and critique must return to Director Context immediately;
- no renderer chat should remain the sole record of an experiment;
- concrete examples/prompts may themselves be diagnostic evidence because examples are visual seeds;
- saved-memory/chat-deletion assumptions that materially affect the method must be preserved as process findings.

GitHub/Drive continuity is authoritative; deleting renderer chats or changing saved-memory controls is not a substitute for archival continuity.

## 9. Fresh-chat continuity and staged historical access

Conceptual memory and visual independence are separate requirements.

### Ordinary continuation/refinement or deliberate revival

When a task explicitly depends on an existing visual branch, a fresh chat may read the registry and inspect relevant archived assets before continuing.

### Surface-independent R0 exploration

When the active handoff calls for independent discovery:

1. read `CURRENT_STATE.md`, `DESIGN_CONTINUITY.md`, Renderer Isolation protocol/checkpoints, active R0 handoff, and current product truth;
2. read textual Drive continuity/registry so historical concepts, user signals, failures, and design judgments are understood;
3. inherit durable abstract discoveries/project laws;
4. do **not** open historical artwork binaries/detailed surfaces before the first independent concept/artwork unless the user explicitly asks or the experiment requires comparison;
5. evaluate the first independent work without resemblance as a criterion;
6. afterward inspect historical images when comparison/inspiration/lineage critique improves the work;
7. label deliberate revival explicitly.

The purpose is not amnesia. It is to prevent visual memory from becoming automatic reproduction.

## 10. Rediscovery rule

A new branch may independently rediscover an earlier surface/idea.

Similarity is not automatically failure. The test is whether the choice is newly earned from product truth, artistic judgment, and current evidence rather than inherited through contextual inertia.

No amount of previous investment creates preservation rights.

## 11. Phase-authority rule

A handoff must preserve the difference between research evidence and project authority.

> **Research discovery != phase transition.**  
> **Assistant/design-team preference != user approval.**  
> **Recent strength != incumbent.**  
> **Metaphor != identity.**  
> **Surface != law.**

Before phase promotion:

1. finish the Drive archive/registry checkpoint;
2. read current GitHub `CURRENT_STATE.md` and active handoff;
3. verify convergence status;
4. obtain explicit mutual convergence where required;
5. only then change current phase authority.

A superseded handoff should be visibly marked non-authoritative rather than left looking active.

## 12. Verification gate

Before declaring a fresh-chat handoff ready:

- verify the active Drive folder/checkpoint exists;
- verify required visual evidence/asset-state wording exists;
- verify registry entry exists;
- verify continuity law updates exist when necessary;
- verify the fresh Drive handoff mirror is in the intended continuity location when used;
- verify GitHub `CURRENT_STATE.md` names the intended active handoff;
- verify the active handoff names the correct completed checkpoints and exact next work;
- verify superseded handoffs are marked superseded/non-authoritative;
- verify no source promotes an unapproved surface or phase;
- verify current product truth has been read only for validation boundaries and no unsupported product claims were introduced.

Only after this verification gate may the old project chat be considered safe to retire.
