## Roadmap to website visual materialization

### W1 — Candidate 04 construction, Method 02 Stages 1–5

Authorized now.

Produce and recursively audit:

1. Semantic Dependency Record;
2. Baseline / Change Evidence Record;
3. Counterfactual Ledger;
4. Two-Person Necessity Matrix;
5. Responsive Semantic Envelope.

Goal: prove the causal/relational geometry before any aesthetic image is attempted.

Output remains textual/structural design evidence, not final artwork.

### W2 — Director construction gate

Director reviews the complete Stages 1–5 package.

If approved, a later explicit gate may authorize Stage 6 candidate-specific Neutral Geometry Scaffold creation.

### W3 — Neutral Geometry Scaffold

**First visual artifact to materialize, but not artwork.**

A deterministic geometry-only scaffold would encode:

- anonymous figure regions/body axes;
- critical contact/support relations;
- continuous shared-condition paths;
- baseline witness regions;
- required negative space;
- necessary occlusion order;
- frozen responsive boundaries.

It carries no palette, material identity, faces, clothing, lighting, texture, brand geometry or final style.

### W4 — Scaffold audit + translation package

Audit the scaffold for geometric correctness, responsive survival, no aesthetic leakage and traceability to the approved Candidate 04 construction.

Then prepare Stage 7 sterile artwork translation and a complete pre-render package.

Reference transfer remains separately controlled.

### W5 — Director execution gate

A complete pre-render package must explicitly state:

- exact scaffold bytes/file, if transferred;
- transfer method / reference-strength control if available;
- sterile renderer-facing text;
- scaffold-leakage disposition;
- accounting/stop consequence;
- unchanged post-render scoring law.

Only explicit Director approval authorizes image execution.

### W6 — First aesthetic website artwork materializes

One approved isolated renderer execution produces the first Method 02 aesthetic candidate.

That returned image is evidence, not automatically the final hero.

It must still pass:

- Hero Brief 02 hard floors;
- Surface Escape;
- S1–S6;
- fixed desktop/mobile Harness 01;
- pixel-based recursive audit.

If it passes, it becomes a credible hero candidate and the visual system can begin converging around independently justified properties.

## Roadmap to application visual assets

There are two distinct meanings of “app assets.”

### A. Design-master app assets

These may materialize in the design/Drive lane before executable app UI exists, once a specific cross-product visual direction is separately authorized.

Examples:

- app icon / symbol master candidates;
- Studio / Stage / Archive visual-language studies;
- character/presence representation studies;
- state-transition/motion studies;
- semantic iconography candidates;
- material/background/empty-state artwork;
- high-fidelity app screen concepts clearly labeled as design proposals.

They must not imply that unimplemented product ontology or WinUI behavior is already frozen.

### B. Implementation-ready/shipping app assets

These arrive later in the engineering program.

Current engineering roadmap requires:

1. complete E0-A;
2. run E0-B..G and converge;
3. freeze post-E0 product-runtime architecture;
4. establish stable-enough Application/persistence/provider/presentation contracts;
5. enter parallel productization including P2 Native Windows application baseline and P4 UI/design implementation convergence.

At P4, approved Drive visual masters can be converted into shipping asset packages and bound to actual semantic Application/view state.

Until then, app visuals are proposals/design masters, not implementation authority.
