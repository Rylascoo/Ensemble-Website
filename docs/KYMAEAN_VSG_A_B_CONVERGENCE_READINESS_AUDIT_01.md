## 5. Architecture conditions for any convergence experiment

A convergence render must preserve the app-derived constraints already established in the crosswalk.

### Identity

- Character != Performer;
- Character != Portrait;
- identity survives representation changes;
- provider/model identity remains secondary.

### Disclosure / posture / salience

```text
Presentation Perspective != Creator Posture
Present != Salient != Obliged
```

A Character-bounded surface must remove prohibited information rather than leave it visible as locked/ghosted privileged state.

### Performance / authority

- creator input != automatic Production mutation;
- Candidate / Take / causal-effect distinctions must remain available when relevant;
- Accepted Take != effective history;
- no `Take Effective` collapse.

### Consequence

- changed current Production is the endpoint;
- meaningful Performance does not require meter movement;
- consequence should first alter understandable human organization/state/affordance;
- history supports `why is this true now?`, not permanent chronology.

### Opportunity

- Current Opportunity is salience/routing authority, not Character intent or obligation;
- one E0 selected Character must not freeze final product design against future very-small-subset attention.

### Technical state

- provider/capability failure never becomes fictional Character behavior;
- Character silence/refusal never looks like a provider failure.

## 7. Accessibility + ARM64/NPU readiness condition

The convergence hypothesis is compatible with the project's ARM64/battery constraints only if relational meaning is **layout/state driven**, not continuously simulated.

Required:

- deterministic layout at rest;
- no continuous graph solver;
- no persistent GPU animation needed to imply a living Scene;
- no decorative idle AI/NPU inference;
- no motion-only salience;
- equivalent programmatic/textual semantics for spatial relation;
- high-contrast / monochrome / reduced-motion / text-scaling survivability;
- solid-material fallback does not destroy hierarchy.

The product feels alive because **Production state changes**, not because the UI is always moving.
