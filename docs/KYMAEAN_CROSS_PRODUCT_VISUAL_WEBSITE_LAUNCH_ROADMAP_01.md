# KYMAEAN CROSS-PRODUCT VISUAL + WEBSITE LAUNCH ROADMAP 01

Status: CANONICAL DESIGN-SEQUENCE ROADMAP / DIRECTOR-APPROVED DIRECTION / IMPLEMENTATION AND LAUNCH VALIDATION REMAIN GATED

Date: 2026-09-04

## 0. Purpose

Define the remaining design/website path from the completed semantic-interaction laboratory through a launch-capable Kymaean visual system, native-app visual asset foundation, exploratory public website, and final cross-surface launch translation.

This roadmap does not replace application engineering authority. `Rylascoo/Ensemble-Project` remains authoritative for what the Windows application actually implements and validates.

## 1. Product-surface separation

Kymaean has two distinct launch surfaces sharing one identity and product truth.

### APP VISUAL — Kymaean for Windows

The native Windows application is the actual creative product.

It owns Production creation and persistence, Characters, Scene/Stage activity, Watch/Direct/Perform/Write creator postures, bounded Perspective, accepted Performance, consequence, causal continuity/history, context, privacy/local state, capability degradation, and eventual supported Windows AI behavior.

The web site does **not** host or replace this application.

### WEB — Kymaean public website

The website is an explorable introduction to a new creative medium, leading into the native Windows application rather than duplicating it in the browser.

Its primary purpose is progressive understanding and exploration:

1. What is Kymaean?
2. Why is it different from chat/content generation?
3. What are persistent Characters?
4. How do Performance, consequence and future possibility connect?
5. How can one authoritative Production support different bounded perspectives?
6. Why do local ownership/privacy and deterministic continuity matter?
7. What does the product truthfully do today?
8. How does a visitor obtain Kymaean for Windows when available?

The website may use deterministic authored interactive demonstrations. It does not require user Productions, provider inference, user accounts, cloud simulation state, or a browser port of Ensemble merely to teach the product.

Required synthesis:

> **APP = immersive working environment. WEB = expressive explanatory environment. SHARED BRAND = one identity and one product truth.**

## 9. Phase F — website experience architecture

Primary tag: `WEB`

Build the public site as an explorable learning journey rather than a browser app or conventional feature-card landing page.

Candidate narrative progression:

1. encounter people / current human situation;
2. introduce persistent Character identity;
3. establish circumstance and bounded access;
4. show Performance as portrayal, not chatbot answer;
5. demonstrate accepted Performance entering Production continuity;
6. demonstrate consequence changing what is possible next;
7. demonstrate bounded Perspective by subtracting information from one shared truth;
8. demonstrate causal history as `Why is this true now?`, not chat history;
9. explain local ownership/privacy/provider separation;
10. explain truthful technical principles and current capability state;
11. provide Windows/Store acquisition path when launch authority exists.

Interactive demonstrations should normally be deterministic authored examples with static/reduced-motion equivalents.

## 13. Cross-product feedback rule

The roadmap is sequential enough to prevent churn but not a waterfall.

When app engineering changes a visually material authority boundary, the design workstream must add the smallest visual-authority reconciliation before relying on stale assumptions.

When native implementation exposes a real interaction/accessibility constraint, patch the smallest design surface rather than redesigning the entire identity.

When website exploration reveals a strong brand property, it may be tested cross-surface but does not automatically become app UI law.
