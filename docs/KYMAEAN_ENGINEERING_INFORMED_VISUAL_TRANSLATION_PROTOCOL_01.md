# KYMAEAN — ENGINEERING-INFORMED VISUAL TRANSLATION PROTOCOL 01

Status: **ACTIVE DESIGN-WORKFLOW PROTOCOL / SUBORDINATE TO PRODUCT AND DESIGN AUTHORITY**  
Date: 2026-09-06

## Purpose

The design lane may perform targeted fresh reads of `Rylascoo/Ensemble-Project` whenever current application architecture, semantics, state transitions, validation boundaries, or implementation direction can make Kymaean's visual identity and interaction design more intuitive.

This protocol does not transfer engineering authority into the design lane and does not allow backend structure to become an accidental aesthetic.

## Source order

For any engineering-informed visual decision:

1. read `Rylascoo/Ensemble-Project/CURRENT_STATE.md` first;
2. read only the roadmap, blueprint, source, tests, or evidence actually needed for the visual/interaction question;
3. distinguish current implemented truth from approved-but-not-implemented architecture and from still-open product/UX ontology;
4. cite or record the exact engineering source used when the translation becomes consequential;
5. return the resulting visual proposal to `Rylascoo/Ensemble-Website` / Drive authority rather than modifying engineering authority from the design lane.

## Translation rule

Engineering facts may inform visual structure, hierarchy, state distinction, motion logic, disclosure, identity continuity, and interaction affordance.

They do **not** automatically select:

- palette;
- typography;
- illustration style;
- layout;
- icon form;
- symbol geometry;
- animation treatment;
- screen architecture;
- product terminology not yet frozen for UI;
- implementation technology.

Always separate:

**ENGINEERING FACT -> DESIGN INFERENCE -> VISUAL PROPOSAL**

A design inference is not engineering law, and an engineering implementation detail is not visual identity merely because it exists in code.

## Current high-value engineering truths for visual intuition

The current engineering repository establishes or preserves several durable semantic distinctions that can safely inform design exploration when relevant:

### Character identity is distinct from Performer/provider identity

Engineering law preserves `Character != Performer`, and provider/model identity remains below model-neutral Application/UI state.

Design inference:

- Character visual identity should remain stable across casting/backend changes;
- provider logos, model names, or execution mechanisms should not become the character's identity or the product's primary visual grammar.

### UI is projection, not authority

Engineering explicitly keeps UI outside causal authority.

Design inference:

- interface states should reveal authoritative state clearly without implying that visual emphasis itself changes canon;
- committed, provisional, rejected, diagnostic, and unavailable states should be perceptually distinguishable where the product exposes them.

### Accepted Performance + authoritative consequence are atomic

Engineering preserves one causal commit in which accepted Performance and retained approved consequences become effective together or neither does.

Design inference:

- when this product event eventually becomes user-visible, the visual transition should feel like one coherent adoption event rather than unrelated partial updates.

### Opportunity is an explicit evolving state

The deterministic path advances from accepted causal commit into a synchronized next Opportunity-bearing state.

Design inference:

- future interaction/motion systems can treat possibility as a changing structural state rather than a generic button/highlight;
- the exact UX remains open until product-runtime architecture freezes it.

### Access precedes Context/relevance

Engineering preserves privacy and disclosure boundaries before semantic selection/model input.

Design inference:

- future disclosure, perspective, context, and character-knowledge surfaces should not visually conflate "available to the system," "allowed for this character," and "currently relevant";
- mystery/asymmetry should arise from legitimate access/perspective boundaries, not arbitrary hiding.

### Claim, fact, knowledge, belief, memory and provenance remain distinct

Engineering keeps these semantic classes separate.

Design inference:

- if exposed in creator-facing UI, visual language should preserve epistemic distinctions rather than flattening all information into one confidence/accent treatment.

### Studio / Stage / Archive remain product spaces, but minimum launch semantics are not yet frozen

The engineering roadmap preserves:

- Studio — what could happen;
- Stage — what happens;
- Archive — what happened, changed, and remains in motion.

Design inference:

- these three spaces are strong candidates for distinct temporal/postural visual roles;
- exact navigation, labels, screen architecture and interaction grammar remain proposals until post-E0 product-runtime architecture resolves them.

## Backend-leak prevention

Do not expose or visually privilege internal implementation details merely because they are architecturally important, including:

- hashes/record IDs;
- provider SDK structure;
- retry machinery;
- test fixture concepts;
- internal type/project names;
- NPU/provider marketing states;
- persistence implementation details;
- deterministic seams that are not creator-meaningful.

A technical structure earns visual representation only when the user needs to understand or act on its product meaning.

## When to scan `Ensemble-Project`

A targeted engineering scan is expected whenever it can materially improve intuition before:

- proposing an app visual identity or screen family;
- defining Studio/Stage/Archive distinctions;
- designing character identity/presence systems;
- designing causal-history/Archive representations;
- designing Opportunity/Take/commit transitions;
- designing context/disclosure/perspective states;
- defining motion/state-change grammar;
- translating website product claims into product imagery;
- handing an app-facing visual proposal to engineering;
- making any visual claim that depends on current product capability.

No separate routine Director approval is required to perform these reads inside already-authorized design work.
